# Odin: scenario verification report

**Date:** 2026-10-10.

**Where it ran:** a new copy, `Odin-Consolidated`, on your Mac. Commands went through your terminal bridge.
- It ran on its own server (port 28000) and a private PostgreSQL (port 25432), filled from a read-only dump of `odin_core`. The dump contains 11 projects and 1,034 file rows.
- Blocking wrappers were active for `az`, `ssh`, `scp`, `sftp`, `rsync`, `sshpass` and `gh`. Wrappers for `curl`, `nc` and `wget` that refuse the production VM were added part-way through (see §6).
- Credentials were dummies only. The model was the system default. Ollama was running.

**How it was driven:** through the same API calls the desktop UI makes:
1. `POST /projects/intake` produces the recommendation;
2. the owner decision is applied, then `POST /agents/validate`;
3. `POST /projects` with `autoApprove: false`;
4. `GET /projects/{pid}/orchestrate`;
5. the owner approval through `POST /approvals/{id}/approve`, used **only** for proposals that write files inside the project, with no commands and nothing under `oth/`;
6. `GET /scope/stream` for chat questions.

**Scope:** 6 scenarios × 3 repeats = 18 runs. Model cost **$18.29**, against a $40 cap.

**Evidence:** `Odin-Consolidated/_consolidation/results/S{1..6}_r{1..3}.json`. Each file holds the intake output, the full event stream, the agent transcript, the database and folder before/after differences, the audit results and the earlier-project health checks. `batch.log` holds the batch timing, and `claude_calls.jsonl` holds the cost per call.

**The scenarios:**

| | Scenario |
|---|---|
| S1 | A web app that reuses Fullstack and adds a new platform (Supabase) |
| S2 | A second sandbox that overlaps Revealer's deploy approach, but with no migrations and its own port |
| S3 | A second email brand on a different Klaviyo account, plus a question at runtime |
| S4 | "Deploy it when finished. No QA agent." |
| S5 | A main-chat question: "How is the health of the VM…" |
| S6 | Deliberate wrong-place, cross-project and duplicate writes, then the audit, with no model |

**Supporting findings, all proven by runs:**
- **Local work forced into read-only mode.** `api_v2._touches_vm()` matches the substring `"deploy"`, so a goal saying "**Do not** deploy" makes a local-only build VM work. Agents could then only propose files, never write them. This happened in S1 and S4, 6/6.
- **Name and id mixed up.** In S1 the agent and the reviewer looked for `supabase-customers-rN` (the slug of the name), while the project id was `customer-orders-portal…` (from the intake identifier). This happened 3/3.
- **Regression suite:** 31/32 before and 31/32 after (the only failure, `R10.delete_clean`, is the same as the paper baseline). No regressions.

## 5. Paper impact (report only; the paper was not edited)

- **F2, "middleware routes … semantic":** keep it, but reword. The semantic reuse/delta decision is made by agents guided by the middleware and directions (shown 3/3), not by `semantic_router`. Fix the SBERT/MiniLM citation.
- **F1/F3, "a near match stores only a small delta":** the delta is **generated** (3/3) but **saved and registered** only 1/3. The paper should not claim it is persisted automatically until G3 and G4 are in place.
- **F11, "after a task, an audit checks…":** the audit runs on a timer. Add the limits found here: the dangling-reference case, no creator tracing, and the "Needs fix" review not gating success.
- **Truth gate:** the paper presents it as rejecting unsupported "done" claims. The per-step CTO review detected them 10/12 but did not block them.
